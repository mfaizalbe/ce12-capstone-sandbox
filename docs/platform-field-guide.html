The Platform, Explained in Plain English

Everything this repository builds and why — written so you can read it once and then explain any part of it to someone else without notes. No prior Kubernetes or AWS knowledge assumed.

Cluster: retail-store-grp5 Region: ap-southeast-1 Order of operations: Terraform → Helmfile → Kustomize
Start here

The one-minute version

Five people built a working online store on AWS, using the same category of tools real engineering teams use to run production software: infrastructure written as code, containers orchestrated by Kubernetes, deployments driven by Git instead of by hand, and a full stack for watching what's happening and knowing when it breaks.

The store itself — a catalogue, a cart, checkout, orders, and a UI that ties them together — isn't the point. It's a stand-in. The five container images are pulled pre-built from AWS's own reference app; nobody on the team wrote or owns that application code. The actual capstone is everything around the app: how do you provision a cluster the same way every time, ship a change without anyone typing a deploy command, get paged the moment something breaks, and know what it's costing you to run.

That's what the rest of this page walks through, roughly in the order you'd explain it to someone who's never seen the repo.

Deployment order

The three layers, in order

Everything in this repo goes down in exactly one sequence, and each layer depends on the one before it existing first. Think of it like building a house: you can't install appliances before the wiring exists, and nobody can move in before the appliances work.

Layer 1 of 3 terraform/

Terraform — the land and the utilities

Builds the empty cluster and everything it needs to exist on AWS. Runs once, changes rarely.

  • A private network (VPC) the cluster lives inside, split across three availability zones with one shared NAT gateway for outbound internet access.
  • The EKS cluster itself, split into two separate groups of servers ("node groups") that never mix:
    • application — 3 to 5 general-purpose servers, open to any workload, running the actual store.
    • observability — 2 to 3 servers, pinned to a single AWS zone (ap-southeast-1c) so their attached disks never get stranded in the wrong zone, and "tainted" so only monitoring software is allowed to land there. A taint works like a bouncer: nothing gets scheduled onto that server unless it explicitly says it's on the list.
  • Permissions, without passwords. Instead of handing a program an AWS access key that can leak, each Kubernetes "service account" (the load balancer controller, Fluent Bit, Grafana, Loki, the tracing collector, the chaos-testing role) is given a scoped-down IAM role it can borrow temporarily, tied to its own identity. This pattern is called IRSA.
  • A shared memory. Terraform needs to remember what it has already built. That memory (its "state") lives in one S3 bucket that all five team members' laptops read and write, with built-in locking so two people can't apply changes at the same time and corrupt it.
↓ once the cluster and network exist
Layer 2 of 3 helm/

Helmfile — the appliances

Installs the platform software the cluster needs before the store can run on top of it. Changes occasionally.

A "Helm chart" is a pre-packaged, configurable install of a piece of software — think of it as an app-store listing, but for Kubernetes. Helmfile is the shopping list that installs several charts in a specific order, since some depend on others:

  1. 1
    AWS Load Balancer Controller — before it installs, a hook applies the Gateway API "CRDs" (see below), since the controller's own resources depend on them existing first.
  2. 2
    external-dns — waits for the load balancer controller, since it needs to see load balancers to point DNS at.
  3. 3
    Prometheus stack (kube-prometheus-stack) — two hooks run first: one binds the reusable, pre-created AWS disks (EBS volumes) for Prometheus/Grafana/Loki/Alertmanager/Kubecost so their data survives a teardown, the other installs Prometheus's own CRDs.
  4. 4
    Loki — the log storage backend.
  5. 5
    OpenTelemetry Operator — the piece that later injects tracing into app pods automatically.
  6. 6
    Kubecost — waits for Prometheus, since it reads its metrics to calculate cost.
  7. 7
    ArgoCD — installed last, ready to take over once the app layer below is applied for the first time.
What's a CRD? A Custom Resource Definition teaches Kubernetes a brand-new type of object it didn't understand before — like adding a new shape of LEGO brick to the box. You can't build anything with a brick that hasn't been added yet, which is exactly why this install order matters: skip ahead, and the next layer fails with a "no matches for kind" error.
↓ once the platform software is running
Layer 3 of 3 manifests/

Kustomize — moving in

Deploys the actual retail store and everything app-specific. Changes constantly — this is what the team iterates on day to day.

  • The five store services — carts, catalog, checkout, orders, ui — each in their own namespace, each following the same file pattern: a namespace, a service account, a config map, a deployment, a service, and (if it needs one) a paired database deployment.
  • Supporting pieces: Fluent Bit (log shipping), the tracing collector, a small cron job that generates fake shopper traffic so dashboards have something to show, the alert rules, and the routing that exposes Grafana/Kubecost/ArgoCD to the outside world.
  • The ArgoCD Application resource itself — this is the one thing in this layer that changes everything downstream. The moment it's applied, ArgoCD starts watching this repo and takes over deploying every future change automatically (see How a change ships).

Two things that are load-bearing but have zero file in this repo: the discord-webhook Secret (Alertmanager → Discord) and the repo-ce12-capstone-sandbox Secret (ArgoCD's read-only git credential). None of this is broken — the account ID doesn't change — but if asked "is this consistent," the honest answer is no, and now you know exactly where.

Networking

How a request gets in

The path a shopper's browser takes to reach the ui pod, and who's responsible for each hop.

Browser requests grp5.sctp-sandbox.com
→
Route 53 DNS auto-managed
→
AWS Application Load Balancer
→
Gateway infra-owned
→
HTTPRoute app-owned
→
ui pod

Nobody manually creates the DNS record — external-dns notices the new route in the cluster and writes the Route 53 entry itself. Nobody manually clicks "create load balancer" in the AWS console either — the AWS Load Balancer Controller provisions and manages the ALB from the same Kubernetes resources.

Those resources are split deliberately in two: a Gateway (the "front door," owned by whoever runs the infrastructure) and an HTTPRoute (the "which path goes to which service" rule, owned by the application team). This is the newer Kubernetes networking standard — Gateway API — chosen over the older, more familiar Ingress resource specifically because that infra/app split mirrors how the rest of this repo is organised, and because it's the direction Kubernetes networking is actually heading.

Knowing when something's wrong

Watching the system

Four separate pillars, all feeding the same Grafana dashboards, all running on the isolated observability node group described above — deliberately, so the system watching for a failure can't be taken down by the same failure it's supposed to catch.

Metrics

A collector scrapes every pod for numbers — CPU, memory, request counts, error rates — every few seconds and feeds them into Prometheus. Grafana then queries Prometheus and draws the dashboards the team actually looks at.

Logs

Fluent Bit runs on every server, tails every container's log output as it's written, and ships it off. Loki stores and indexes it, turning it into something searchable from inside Grafana — like a search engine, but for log lines.

Traces

The trickiest of the three, because it means following one shopping request as it hops ui → catalog → carts → checkout to see exactly where time got lost. Normally that requires editing each service's source code — not an option here, since the team doesn't own that code.

Instead, the OpenTelemetry Operator injects tracing automatically at the moment a pod starts, based on an annotation on that pod — zero source code touched. Java and Node.js services get it via an extra init container; the Go service gets it through a lower-level technique (an eBPF sidecar) since Go doesn't support the same injection method. About 1 in 10 requests gets traced, to keep the volume manageable, and every trace ends up in AWS X-Ray, viewable straight from Grafana.

Alerts

Prometheus continuously checks two rules against reality:

AlertSeverityFires when
NodeNotReadycriticalA server hasn't reported itself healthy for more than 15 seconds — usually because it was terminated or crashed.
RetailStorePodsPendingwarningOne or more app pods have been stuck waiting to start for more than 5 seconds — the expected knock-on effect of losing a node.

When either fires, Alertmanager pushes a message straight into the team's Discord — a small trick makes this work: Discord happens to accept the exact webhook format Slack uses, so Alertmanager's built-in Slack integration works unmodified, just pointed at a Discord URL.

Cost

Kubecost reads the same Prometheus metrics everything else uses and breaks the AWS bill down by Kubernetes namespace — so "how much does checkout cost us this month" gets an actual number, instead of one lump AWS invoice with no way to attribute it.

Continuous delivery

How a change ships

After the very first manual apply, a human never runs a deploy command again — ArgoCD, itself deployed as an app in this repo, takes over watching the repo it lives in.

Someone pushes to main
→
ArgoCD notices ~3 min
→
Applies it to the cluster
→
Prometheus checks health
→
Broken? Discord

ArgoCD's Application resource is configured with two behaviours worth knowing by name, since they explain almost everything about how the cluster stays in sync:

  • selfHeal — if anyone manually changes something inside the cluster by hand (say, via kubectl edit), ArgoCD notices the drift from what's in Git and quietly reverts it back within a few minutes. Git — not whatever's currently running — is treated as the source of truth.
  • prune — if a file is deleted from manifests/ in the repo, the matching resource is deleted from the cluster too, automatically.

Because the repo is private, ArgoCD needs a read-only key to clone it — that's set up once, before the very first apply, so ArgoCD can start syncing immediately instead of sitting in an auth-error state.

Proving it, not just trusting it

Breaking it on purpose

Anyone can write an alert rule that looks correct on paper. The only way to know it actually fires under a real failure is to cause one — deliberately, safely, and on a schedule the team controls.

AWS Fault Injection Service (FIS) is aimed — via a narrowly scoped IAM role that can only terminate EC2 instances, nothing else — at exactly one target: 67% of the instances in the application node group. Never the observability node group, on purpose: that's the same isolation decision from the layers section above, and it's what stops this experiment from also killing the very system that's supposed to detect and report on the failure it causes.

  1. 1
    FIS terminates roughly two-thirds of the application node group's real EC2 instances.
  2. 2
    Those nodes stop reporting healthy — NodeNotReady starts counting down.
  3. 3
    Because it's an EKS managed node group, AWS automatically launches replacement instances without anyone asking.
  4. 4
    Kubernetes evicts the pods that were on the dead nodes and reschedules them onto whatever's healthy — which briefly leaves some pods Pending, tripping RetailStorePodsPending.
  5. 5
    Both alerts fire, Discord gets two messages, and the Grafana panel turns red with "FIRING!"
  6. 6
    Once the replacement nodes join and the pending pods land on them, both alerts clear themselves — no one touches anything.
The reasoning

Why we chose this

Every major tool choice is written up as a full Architecture Decision Record in docs/adr/, including the options that were considered and rejected. Condensed to one line each:

ADRChoseOverBecause
0001Amazon EKSPlain EC2 + DockerManaged control plane, built-in self-healing/scaling, and the industry-standard way to demonstrate SRE practice.
0002Gateway APIClassic IngressWhere Kubernetes networking is actually heading, and it cleanly splits infra-owned routing from app-owned routing.
0003Helmfile + Kustomize splitOne tool for everythingThird-party software needs Helm's install/upgrade machinery; the team's own plain YAML doesn't need a chart at all.
0004Self-hosted Prometheus/Grafana/Loki/OTelCloudWatch, or paid SaaSFree beyond storage already being paid for, and the skills transfer to real jobs better than a CloudWatch-only setup.
0005Separate, tainted observability node groupOne shared node groupSo the chaos demo can kill app servers without also killing the system meant to detect the failure.
0006S3 remote state with native lockingLocal state, or S3 + DynamoDBOne shared AWS resource covers both storage and locking for five people applying from their own laptops.
0007KubecostAWS Cost Explorer aloneCost Explorer can't say "catalog cost $X this month" — only per-namespace breakdown can.

Honest about scope

What we deliberately left out

Good defence in Q&A is naming these before someone else does. None of these are oversights — they're scope decisions for a one-month, five-person learning project, not a production system.

  • No HTTPS — every service is plain HTTP; production would use TLS via ACM or cert-manager.
  • No CI pipeline — no automated image building, testing, or scanning; the app images are pre-built and deployed as-is.
  • No secrets manager — things like the Discord webhook URL sit in plain Kubernetes Secrets, not AWS Secrets Manager or Vault.
  • No multi-environment — one cluster, one environment; production would separate dev/staging/prod with promotion gates.
  • No auto-scaling — neither pods nor nodes scale automatically with load.
  • No RBAC — every team member has cluster-admin access; production would scope permissions per role.
  • No network policies — any service can talk to any other service inside the cluster, unrestricted.
  • Single region — no cross-region redundancy or disaster recovery.
Jargon, defused

Glossary

The dozen terms most likely to come up in a question you weren't expecting.

ALB
AWS Application Load Balancer — the actual internet-facing thing that receives traffic, provisioned automatically by the load balancer controller.
CRD
Custom Resource Definition — teaches Kubernetes a brand-new type of object it didn't understand before. Nothing of that new type can be created until its CRD is installed.
GitOps
The practice of treating a Git repo as the single source of truth for what should be running, with a tool (here, ArgoCD) automatically reconciling reality to match it.
Helm chart
A pre-packaged, configurable install of a piece of software for Kubernetes — the unit Helmfile installs.
IaC
Infrastructure as Code — describing servers and networks as text files instead of manual console clicks, so the setup is repeatable and reviewable.
IRSA
IAM Roles for Service Accounts — lets a specific Kubernetes identity borrow scoped AWS permissions temporarily, with no access key or password stored anywhere.
Namespace
A named subdivision inside one cluster — each of the five services and each platform tool gets its own, keeping their resources separate.
Node group
A set of EC2 servers managed together as one unit inside the cluster. This project has two: application and observability.
PV / PVC
PersistentVolume / PersistentVolumeClaim — Kubernetes' way of attaching a real disk (here, an AWS EBS volume) to a pod so its data survives a restart.
Sampling
Tracing only a fraction of requests (10% here) instead of every single one, to keep the volume of trace data manageable and affordable.
Taint / toleration
A taint blocks anything from being scheduled onto a server unless it carries a matching toleration — used here to reserve the observability node group for monitoring pods only.
Webhook
A URL that a service calls automatically when something happens — used two different ways here: Kubernetes calls one to auto-inject tracing into new pods, and Alertmanager calls one to post into Discord.

Architecture & trade-offs

Isn't a full Kubernetes cluster overkill for five small microservices?

Bluntly, yes, for the workload size alone — ADR 0001 names this directly as something the decision rules out: "lowest-cost deployment option for small workloads." The justification isn't workload size, it's the learning objective. The capstone exists to demonstrate SRE and cloud-native practice — self-healing, managed scaling, Helm-based delivery — and EKS is the platform that lets the team show that convincingly.

Why split deployment across Helmfile and Kustomize instead of one tool?

They solve different problems. Helmfile installs third-party software — the load balancer controller, Prometheus, ArgoCD — that ships as versioned Helm charts with CRDs and upgrade lifecycles; Kustomize has no concept of any of that. Kustomize applies the team's own plain YAML for the five services, which never had a Helm chart and didn't need one. Full comparison in ADR 0003.

Why Gateway API instead of the far more common Ingress resource?

Gateway API is where Kubernetes networking is heading, and it splits cleanly into infrastructure-owned config (Gateway) and application-owned config (HTTPRoute) — the same ownership split used everywhere else in this repo. The honest cost, acknowledged in ADR 0002: fewer examples online, and for a single hostname it's more machinery than Ingress would have needed.

Why one NAT gateway instead of one per availability zone?

Cost — single_nat_gateway = true in terraform/vpc.tf. One NAT gateway serves all three AZs' private subnets. It's a real single point of failure for the cluster's outbound internet access (inbound traffic goes through the ALB, unaffected), but running three would triple that specific cost for a project with no production SLA to protect.

Gateway API + external-dns — what are the actual components, and how do they work together?

Five pieces, each owned by a different layer:

  • GatewayClass (aws-alb) — infra-owned, says "this cluster knows how to build ALBs"
  • Gateway (retail-store-gateway) — infra-owned, the shared "front door," one per cluster here
  • HTTPRoute — app-owned, one per exposed hostname (ui, Grafana ×2, Kubecost, ArgoCD), all pointing back at that one Gateway via parentRefs
  • Service — the actual backend each HTTPRoute forwards to
  • TargetGroupConfig — optional, attaches an ALB health check to a route

The AWS Load Balancer Controller watches all of the above and provisions the real ALB, listener, and target groups. external-dns separately watches every HTTPRoute's hostnames: field (its gateway-httproute source, set in helm/values/external-dns.yaml.gotmpl) and auto-creates the matching Route 53 record. Net result: one ALB, one Gateway, five hostnames split purely by HTTPRoute host-matching — and nobody ever touches the Route 53 console.

Reliability & failure modes

Every deployment shows replicas: 1. Doesn't the app actually go down during the node failure demo?

Yes — worth saying plainly before it's asked. Every one of the five services (ui, catalog, carts, checkout, orders) and every database runs as a single replica. When FIS kills a node, whatever was running on it — app pod or database — is genuinely unavailable for the seconds-to-minutes it takes Kubernetes to reschedule it onto a healthy node. The demo shows self-healing (nothing stays down, no human intervenes), not zero-downtime failover, which would require multiple replicas spread across nodes — this project doesn't run any.

What happens to the data in carts, checkout, orders, or catalog's databases if their pod restarts?

It's gone. carts-dynamodb and checkout-redis mount no volume at all — DynamoDB Local and Redis are running purely in-memory. catalog's MySQL and orders' PostgreSQL each mount an emptyDir volume, which is tied to the pod's own lifecycle rather than persisted storage — the moment that pod is deleted or rescheduled to a different node, the volume and everything in it is wiped and the database starts empty again. None of the four databases use a PersistentVolumeClaim. It's a real, easily-defensible gap: production would back every one with an EBS-backed PVC — the way Prometheus, Grafana, Loki, and Kubecost already are via the retained-storage pattern in helm/retained-storage.yaml — or a managed AWS database (RDS, ElastiCache, real DynamoDB instead of dynamodb-local).

You don't define any SLIs or SLOs. How do you know if the system is "reliable"?

We don't, formally — there's no error budget or availability target defined anywhere in this project. What exists is the tooling an SLO practice would sit on top of: Prometheus is already collecting the request/error/latency metrics an SLI would be defined from, and Grafana/Alertmanager are already wired to page on threshold breaches. Defining actual SLOs (for example, "99% of requests under 300ms") and an error-budget policy around them is the natural next step, out of scope here.

NodeNotReady fires after only 15 seconds. Isn't that far too sensitive for a real production alert?

For production, yes — that threshold would produce constant noise from routine node replacements, rolling upgrades, or brief network blips. It's tuned tight on purpose here because it needs to fire visibly within a live demo window. A production-grade version of the same rule would typically use a multi-minute for: duration to filter out exactly that kind of transient noise.

Security

Every team member has cluster-admin. What stops someone from accidentally deleting production?

Nothing, currently — a named limitation, not an oversight. access_entries in terraform/eks.tf grants every listed cluster_admins user the full AmazonEKSClusterAdminPolicy. For a five-person team sharing one AWS account with no real production traffic, the coordination cost of role-scoped RBAC wasn't judged worth it within a one-month window. A production version would scope each contributor to namespace-level edit/view roles, with admin reserved for a small platform team.

The Discord webhook is stored as a plain Kubernetes Secret. Isn't that insecure?

A Kubernetes Secret is base64-encoded, not encrypted — anyone with get secret permission in that namespace (which, per the previous answer, is everyone on the team) can read it in plaintext. It's an accepted risk at this trust level: one team, one AWS account, a webhook URL that at worst lets someone post a fake alert into the team's own Discord. Production would use AWS Secrets Manager or Vault with envelope encryption and tighter access scoping.

How do you stop a compromised pod in one namespace from reaching another namespace's database?

Currently you can't — there are no NetworkPolicies anywhere in the cluster, so any pod can reach any other pod or service across every namespace by default. Named directly in the README's known limitations. Production would add default-deny NetworkPolicies per namespace, with explicit allow rules only for the traffic paths actually needed (e.g. checkout → checkout-redis, nothing broader).

Why is everything plain HTTP instead of HTTPS?

The shared ALB Gateway listener was set up without TLS to keep the networking layer simple within the timeframe. It has a real downstream consequence: ArgoCD's server.insecure: "true" setting exists specifically to stop ArgoCD from redirecting to HTTPS and creating an infinite redirect loop behind that plain-HTTP listener. Production would terminate TLS at the ALB using an ACM certificate, or cert-manager for a fully in-cluster PKI.

Cost

What is this actually costing to run?

Check Kubecost live — that's exactly the question it exists to answer, broken down by namespace rather than as a single AWS invoice line. The known fixed cost drivers: the EKS control plane's hourly fee, five to eight running t3.medium EC2 instances across the two node groups, the retained EBS volumes for Prometheus/Loki/Grafana/Alertmanager/Kubecost, one NAT gateway, and one ALB.

Kubecost itself needs infrastructure to run — isn't a cost tool that costs money a bit circular?

It only costs the EBS volume and compute it consumes as one more pod on the observability node group — no license fee, since the project stays within Kubecost's free tier, which is sufficient for a single small cluster. ADR 0007 covers this trade-off directly.

GitOps & deployment safety

ArgoCD auto-syncs with selfHeal and prune on. What stops a bad commit to main from immediately breaking the live app?

Nothing currently does — there's no CI pipeline, no automated test gate, no staging environment, and no manual approval step between a commit landing on main and ArgoCD applying it cluster-wide, typically within about three minutes. Named directly in the limitations: no CI/CD pipeline, no multi-environment. Production GitOps setups solve this with a promotion pipeline — CI validates the change, it lands in staging first, and only a passing, reviewed change gets promoted to the path ArgoCD watches for production.

How would you roll back a bad deploy, given nobody runs kubectl apply anymore?

git revert the offending commit and push to main — ArgoCD picks it up the same way it picks up any other commit, within about three minutes. ArgoCD's UI also keeps a history of previously synced revisions that can be rolled back to directly, as a faster manual fallback.

ArgoCD's repo-server can't run envsubst — why does that matter?

A handful of manifests (manifests/adot/serviceaccount.yaml, manifests/adot/opentelemetrycollector.yaml) used to rely on ${AWS_ACCOUNT_ID}/${EKS_CLUSTER_NAME}/${AWS_REGION} being substituted at apply time. ArgoCD's repo-server runs a plain kustomize build with no substitution step, so those values are hardcoded directly into the manifests instead. Reasonable for a single, fixed cluster and account — it would need revisiting for a genuinely multi-environment setup.

Is ArgoCD set up as "app of apps," or one single Application?

One single Application (manifests/argocd/application.yaml, name retail-store) pointing at the whole manifests/ folder — all 13 subdirectories sync as one unit. No parent/child app-of-apps hierarchy anywhere in the repo. That's the right amount of complexity for one cluster and one team; app-of-apps would earn its keep if different services needed independent sync policies, or the project spanned multiple clusters/teams.

Chaos engineering rigor

Why terminate 67% of the application node group instead of 100%?

That's the configured value (instanceTerminationPercentage: "67" in the FIS experiment template) — it isn't written down anywhere why 67 specifically, so the honest answer is "that's what's configured," not a documented design rationale. A reasonable read: high enough to force a real, visible node-loss and pod-rescheduling event without necessarily terminating every instance in the group at once.

Does this chaos test anything besides "an EC2 instance disappears"?

No — explicit in ADR 0008's trade-offs. FIS was chosen specifically because it terminates real EC2 instances, an authentic trigger for NodeNotReady, at the cost of not testing other failure classes — network latency, packet loss, pod-level faults — that a dedicated in-cluster chaos framework like Chaos Mesh would cover.

Why does the experiment only ever target the application node group, never observability?

On purpose, and it's the same reasoning as the dedicated observability node group itself (ADR 0005): if the chaos experiment could also kill a Prometheus or Alertmanager pod, it would risk taking down the very system that's supposed to detect and report the failure it just caused — undermining the point of the demo entirely.

Observability depth

Only 10% of requests are traced. How would you catch a bug that only shows up 1% of the time?

At a flat 10% sample rate you'd likely still catch it eventually across enough traffic, but any single occurrence has a 90% chance of being missed. The sampling here (parentbased_traceidratio at 0.1, set in manifests/otel-instrumentation/instrumentation.yaml) is a flat head-based rate chosen to keep trace volume and X-Ray cost predictable. Production systems chasing rare intermittent failures more often use tail-based sampling, which decides whether to keep a trace after seeing it — always keeping traces with errors or high latency — rather than before.

Metrics, logs, and traces all live on one dedicated node group. What if that node group itself goes down?

Then the team is flying blind until it recovers — there's no secondary observability path. That's the direct trade-off named in ADR 0005: isolating observability protects it from the application-side chaos experiment, but the stack still has no redundancy of its own — it runs on a small 2–3 node group with no multi-AZ spread, since it's deliberately pinned to a single AZ for EBS volume affinity.

If someone tears the whole cluster down and rebuilds it, do the Grafana dashboards and historical metrics survive?

Yes, deliberately. The retained EBS volumes (helm/retained-storage.yaml, bound via a Helmfile presync hook using fixed volume IDs) and the S3 buckets for Loki and Terraform state are all designed to outlive a helmfile destroy / terraform destroy cycle. They're only deleted if someone does it manually.

Why Fluent Bit for logs instead of Promtail or Grafana Alloy?

Not written down as a formal decision anywhere — no ADR argues Fluent Bit over Promtail/Alloy specifically, so this one's an inference, not a documented choice. The defensible reason, from what's actually configured in manifests/fluentbit/fluent-bit.yaml: one Fluent Bit agent fans every log line out to two destinations at once — CloudWatch Logs and Loki. Promtail only ships to Loki; getting the CloudWatch half too would mean running a second agent alongside it. Fluent Bit is also AWS's own default recommendation for EKS Container Insights, so the CloudWatch integration came almost for free.

What are the different sources of logs, and where does each one go?

Three separate streams, each shipped to both CloudWatch Logs and Loki:

  • Application — stdout/stderr from every pod, i.e. the five store services themselves
  • Dataplane — Kubernetes' own node-level components (aws-node, kube-proxy, kubelet)
  • Host — raw OS logs from the node itself (dmesg, messages, secure), via the systemd journal
OpenTelemetry and Node Exporter both feed Prometheus. What's the actual difference in what they collect?

Different altitudes, zero overlap. Node Exporter (bundled by default with kube-prometheus-stack, never disabled here) reports on the server itself — CPU, memory, disk, network of the underlying EC2 host — with no idea any app is even running on it. ADOT (the OTel collector) does the opposite: it discovers pods via their prometheus.io/scrape annotations and pulls application-level metrics — JVM stats, request counts, per-endpoint latency — the kind of thing only the app itself knows about. Both eventually land in the same Prometheus, but nothing about "is this node healthy" ever comes from ADOT, and nothing about "is checkout throwing errors" ever comes from Node Exporter.

How are the app metrics actually collected, end to end?

Each deployment exposes a metrics endpoint and says so via annotation — catalog/checkout on /metrics, carts/orders/ui (Spring Boot) on /actuator/prometheus, all port 8080. ADOT's kubernetes-pods job scans every pod in the cluster, reads those annotations to build the real scrape target, pulls the metrics every 60 seconds, and remote-writes the result into Prometheus. Worth knowing precisely: the in-cluster Prometheus never scrapes the app pods itself — ADOT does the scraping, Prometheus just receives what's pushed to it.

Why use CloudWatch for traces?

Small correction on the premise first: it isn't CloudWatch, it's AWS X-Ray specifically — a separate AWS service (check the awsxray exporter in manifests/adot/opentelemetrycollector.yaml, and the Grafana datasource literally named "AWS X-Ray"). As for why X-Ray over a self-hosted backend like Tempo or Jaeger: ADR 0010 only documents why auto-instrumentation was chosen, not this specific backend choice, so treat this as a reasoned guess rather than a written decision — X-Ray needs no extra self-hosted, EBS-backed storage component the way Tempo would, and the IAM wiring for it (adot_irsa's trace-write permission, grafana_irsa's trace-read permission) was already in place for the rest of the stack.

How would you actually use traces for root-cause analysis?

A trace follows one request as it hops ui → catalog/carts/orders/checkout, so a slow or failing request's waterfall shows exactly which downstream call ate the time or threw the error — open it in the X-Ray datasource from Grafana and read the span breakdown directly. Two honest limits worth naming before an instructor finds them: only 10% of requests are sampled, so a rare, low-frequency bug can easily be missed entirely; and there's no trace-ID-to-log correlation wired up anywhere — Fluent Bit doesn't inject trace IDs into log lines, so linking a specific trace back to its logs is a manual, timestamp-based lookup, not a one-click jump.
